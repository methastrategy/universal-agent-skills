# Verifying a Claimed Remediation (ตรวจรับงานที่ผู้ใช้อ้างว่า "ปิดเสร็จแล้ว")

คู่มือตรวจสอบงานแก้ไขที่ผู้ใช้/ทีมอื่นอ้างว่าทำเสร็จแล้ว — เน้นยืนยันด้วยหลักฐานจากการรันจริง ไม่ใช่การอ่าน commit message

---

## 1. หลักการ: อ้างว่าปิดแล้ว ≠ ปิดแล้ว

รายงานที่ได้รับมักมีรูปแบบ “จัดการปิดงาน P0–P5 ทั้งหมดเรียบร้อยแล้ว: 1)… 2)… 3)…” การตรวจรับที่ถูกต้องต้อง:

- **ยืนยันทีละข้อ** แยกแต่ละข้อ ไม่รวบเป็นข้อเดียว
- **รันของจริง** ไม่อ่าน diff แล้วเชื่อ — guard ที่ “เพิ่มแล้ว” ต้องพิสูจน์ว่าบล็อกจริง
- **รายงานส่วนที่ยังขาดตามจริง** แม้ผู้ใช้ประกาศว่าครบแล้ว

โครงสร้างรายงานที่ผู้ใช้ยอมรับ: `✅ ที่ยืนยันผ่าน` (พร้อม transcript จริง) → `⚠️ จุดที่ยังมีปัญหา` (พร้อมเหตุผล) → `⚡ สิ่งที่ทำต่อ`

## 2. ขั้นตอนตรวจรับ

### 2.1 ยืนยัน commit มีอยู่จริงและมีเนื้อหาที่อ้าง
```bash
git log --oneline -8
git show <sha> --stat
git show HEAD:<path> | grep -c "<pattern>"   # ยืนยันว่าโค้ดอยู่ใน COMMITTED blob ไม่ใช่แค่ working tree
```
การอ่านไฟล์ใน working tree ไม่พอ — โค้ดที่อ้างว่า commit แล้วอาจยังไม่ถูก commit

### 2.2 รัน guard แล้วดู exit code จริง
```bash
python build_x.py            # ต้องเห็น [BLOCKED] และ exit code = 1
python build_x.py >/dev/null 2>&1; echo "exit=$?"
```
ข้อควรระวัง: `python build_x.py | tail -5; echo $?` รายงาน exit code ของ `tail` ไม่ใช่ของสคริปต์ — ใช้ redirect แยก หรือ `${PIPESTATUS[0]}`

### 2.3 ยืนยันว่า artifact ไม่ถูกแตะ
เทียบ md5 + mtime ก่อนและหลังรัน:
```bash
md5sum <artifact>; ls -la --time-style=+%F_%T <artifact>
```

### 2.4 ทดสอบ path ของ `--force` แบบย้อนกลับได้
ใช้เฉพาะกับ artifact ที่ git-tracked และ working tree สะอาด:
```bash
md5sum <a>                          # จดค่าเดิม
python build_x.py --force           # ต้องเห็น "Created safety backup: ...bak_<ts>"
cp <a>.bak_<ts> <a> && rm <a>.bak_<ts>
md5sum <a>                          # ต้องตรงค่าเดิม
git status --porcelain              # ต้องว่าง
```
ถ้าไฟล์ backup ไม่ถูก ignore จะกลายเป็น untracked file ปนใน repo — ตรวจ `.gitignore` ว่ามี `*.bak_*`

### 2.5 เทียบผลลัพธ์ของ refactor แบบ byte-identical
```bash
md5sum <artifact>; git show HEAD:<artifact> | md5sum   # ต้องตรงกันทุ้งคู่
```
นี่คือหลักฐานเดียวที่พิสูจน์ว่า refactor ไม่เปลี่ยนพฤติกรรม — “รันผ่าน” ไม่ใช่หลักฐาน

### 2.6 ตรวจว่าครบ “ทั้งชุด” ไม่ใช่แค่ไฟล์ที่อ้าง
```bash
git ls-files | wc -l
git ls-files --error-unmatch <sibling>   # ต้องตรวจทุกพี่น้อง ไม่ใช่แค่ไฟล์ที่อ้าง
```
ข้อผิดพลาดที่พบบ่อย: อ้างว่า track ทั้งหมด แต่จริง ๆ แล้วมีแค่ 1 ใน 8 ไฟล์ — ให้รายงานจำนวนที่ยังขาด

## 3. การตรวจ guard เชิงออกแบบ

- **Content-based guard > mtime guard**: หลัง commit หรือ checkout ใหม่ mtime ของ generator จะใหม่กว่าทุก artifact เสมอ → mtime guard ไม่เคย fire อีกต่อไป ใช้การเทียบขนาด/เนื้อหาของ artifact กับ payload ที่ generator จะเขียนแทน
- **Port ให้ครบทุกตัวในตระกูล**: guard ที่ใส่แค่ 1 ตัวจาก 3 ตัวที่เขียนลงโฟลเดอร์เดียวกัน = อีก 2 ตัวยังทับงานได้เงียบ ๆ
- **ตรวจว่าออกแบบ artifact ไหน**: generator ที่เขียนไฟล์ในโฟลเดอร์ที่มี artifact คนละชุด = คนละ flow

## 4. รูปแบบรายงาน

```
✅ ผ่าน — <ข้อ> : <หลักฐานจริง 2-3 บรรทัด>
⚠️ ยังไม่ครบ — <ข้อ> : <หล่าเหตุ> + <คำสั่งที่ยืนยัน>
⚡ สิ่งที่ทำต่อ — <คำสั่งเดียวที่รันได้ทันที>
```

หลีกเลี่ยง: การยืนยันรวม ๆ ว่า “เรียบร้อย”, การอ้าง commit message แทนหลักฐานการรัน, การไม่ระบุว่าอะไรยังค้าง
