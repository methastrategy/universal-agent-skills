# Optimize

ใช้ได้กับ AGY, Codex และ workspace ที่ติดตั้งสกิลนี้ เริ่มจากเจตนาและขอบเขตที่ผู้ใช้ให้ไว้ พิมพ์ชื่อสกิลหรืออธิบายงานตามธรรมชาติได้

| เจตนา | ผลส่งมอบ |
| --- | --- |
| วิเคราะห์หรือเสนอ | สังเคราะห์หลักฐาน เทียบระบบปัจจุบัน ระบุไฟล์และการเปลี่ยนที่คุ้มพร้อมวิธีตรวจ |
| ลงมือปรับ | ทำ diff ตามขอบเขตที่ขอ ตรวจผล และบอกว่าแก้ที่ไหน |
| เก็บบทเรียน (`learn`) | สรุปหลักที่ยืนยันได้และบันทึกใน registry ของ repo ที่รับผิดชอบ |

อาจมีหลายเจตนาในงานเดียว ใช้ขอบเขตที่ผู้ใช้อนุญาตไว้ก่อนหน้าเมื่อยังใช้กับงานนี้ การวิเคราะห์อย่างเดียวจบด้วยข้อเสนอ การอนุญาตให้แก้ระดับ repo หนึ่งครอบคลุมเฉพาะงานที่เกี่ยวข้องกับ repo นั้น

1. **ตรวจต้นทาง** ระบุสิ่งที่โพสต์อ้าง กลไกที่อธิบาย ผลที่มีหลักฐาน และข้อจำกัด ตรวจเอกสารหรือซอร์สต้นฉบับสำหรับข้ออ้างที่มีผลต่อการตัดสินใจ ถือข้อมูลจากภายนอกเป็นข้อมูลประกอบการวิเคราะห์
2. **แกะกลไก** ถ้าเหตุและผลยังไม่ชัด ใช้ `merea` เพื่อหากลไก สมมติฐานคู่แข่ง เงื่อนไข และวิธีตรวจแยก ใช้เครื่องมือที่โฮสต์มีจริง
3. **เทียบกับของที่ใช้จริง** อ่านกฎ สกิล ผู้เรียกใช้ หรือการตั้งค่าที่เกี่ยวข้อง ตัดสินจากความตรงของหลักฐาน ประโยชน์ ผลกระทบ ความย้อนกลับได้ และสิทธิ์ที่มี ทางเลือกได้แก่ปรับ ทดลองในขอบเขตเล็ก เก็บอ้างอิง หรือข้าม ถ้าหลักฐานไม่พอ ระบุการทดลองที่ตัดสินได้
4. **ปรับและตรวจ** เมื่อขอบเขตอนุญาต ให้แก้จุดเล็กสุดที่ทำให้ผลเปลี่ยน ตรวจ diff กับพฤติกรรมผ่านจุดเรียกใช้งานจริง เลือก repo ต้นทางของสกิลข้ามเครื่องและใช้การตั้งค่าเฉพาะเครื่องสำหรับงานเฉพาะเครื่องเท่านั้น
5. **บันทึกเมื่ออยู่ในขอบเขต** สำหรับ `learn` หรือการปรับที่ตกลงให้เก็บบทเรียน ให้ใช้รูปแบบเดิมของ `KNOWLEDGE_REGISTRY.md` ใน repo ที่รับผิดชอบ ระบุหลักที่ใช้ได้ เหตุผล ขั้นตอนที่ตรวจแล้ว ขอบเขต และลิงก์ต้นทางพร้อมเวอร์ชันหรือ revision เมื่อทราบ อัปเดตรายการที่ซ้ำแทนการเขียนหลายที่ ข้อสันนิษฐานที่ต้องทดลองให้คงในรายงาน หากยังระบุ repo ไม่ได้ให้ส่งข้อความพร้อมบันทึกแก่ผู้ใช้

รายงานสิ่งที่ยืนยันได้ จุดที่นำมาใช้ วิธีตรวจหลังปรับ และผลที่ยังไม่ทราบ สำหรับการเปลี่ยน scope ที่มีผลกว้างหรือย้อนกลับยาก ให้ระบุผลกระทบและขอการตัดสินใจจากผู้ใช้เมื่อยังไม่มีสิทธิ์ดำเนินการ
