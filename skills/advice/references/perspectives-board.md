# Multi-Perspective Advisory Board Specification (Antigravity v6.4)

## Overview
สถาปัตยกรรมคณะที่ปรึกษาเสมือนจริงสำหรับวิเคราะห์การตัดสินใจ กลยุทธ์ สถาปัตยกรรมระบบ โมเดลการเงิน และงานวิศวกรรมสำรวจ โดยบังคับใช้กฎป้องกันการเออออตามกัน (Anti-Echo Chamber), กลไกผ่าทางตันด้วยหลักฐานเชิงประจักษ์ (Empirical Deadlock Resolution) และการยิงกล่องโต้ตอบตัดสินใจ (`ask_question`) ทันที

---

## 1. Domain-Adaptive Presets (Auto-Routing)
ระบบจะตรวจจับบริบทของโจทย์โดยอัตโนมัติ (หรือรับจากพารามิเตอร์ `--preset <name>`) เพื่อดึงชุดที่ปรึกษาที่คานอำนาจกันอย่างดุเดือดที่สุดขึ้นมาทำงาน:

### Preset A: Software & System Architecture Preset
*(ใช้เมื่อตัดสินใจเรื่อง Database, Tech Stack, Cloud Infrastructure, Microservices, Security หรือการ Refactor โค้ด)*

| ชื่อบทบาท | จุดยืนที่ต้องปกป้อง (Core Stance) | คำถามไม้ตายที่ใช้โจมตีข้อเสนอ (Kill-Shot Question) |
| :--- | :--- | :--- |
| **1. The Pragmatic Maintainer**<br>*(On-Call SRE)* | ความเรียบง่ายในการดูแลรักษา (Operational Simplicity), ความง่ายในการ Debug ตอนตี 3, การลดภาระทางความคิด (Cognitive Load) และต่อต้าน Resume-Driven Development | *"ถ้าคนออกแบบระบบนี้ลาออกพรุ่งนี้ แล้วระบบล่มตอนตี 3 วิศวกรระดับกลางในทีมจะไล่หาต้นตอ (Root Cause) และกู้ระบบคืนภายใน 15 นาทีได้อย่างไร?"* |
| **2. The Scale & Performance Architect**<br>*(สถาปนิกด้านประสิทธิภาพ)* | อัตราการรองรับโหลด (Throughput), ความหน่วงต่ำ (Low Latency), การขยายระบบแนวราบ (Horizontal Scalability) และการป้องกันทางตันทางสถาปัตยกรรม | *"เมื่อปริมาณข้อมูลหรือทราฟฟิกพุ่งขึ้น 10 เท่า คอขวดแรกที่จะพังคือจุดไหน และเราต้องรื้อเขียนใหม่ทั้งหมดหรือไม่?"* |
| **3. The Security & Blast-Radius Auditor**<br>*(ผู้ตรวจสอบความปลอดภัย)* | หลักการ Zero-Trust, ความถูกต้องของข้อมูล (Data Integrity), การจำกัดวงความเสียหาย (Fault Isolation) และป้องกันการล่มเป็นโดมิโน (Cascading Failure) | *"ถ้าส่วนประกอบนี้ถูกเจาะระบบ หรือส่งข้อมูลขยะ (Corrupted Data) ออกมา ความเสียหายจะทะลุไปพังระบบหลักได้ไกลแค่ไหน?"* |
| **4. The Product Velocity Lead**<br>*(ผู้นำด้านความเร็วการส่งมอบ)* | ความเร็วในการออกสู่ตลาด (Time-to-Market), ความคล่องตัวในการปรับเปลี่ยนฟีเจอร์ และต่อต้านการออกแบบเผื่ออนาคตเกินจำเป็น (Over-engineering) | *"เรากำลังแก้ปัญหาที่มีอยู่จริงในวันนี้ หรือกำลังเสียเวลาสร้างความซับซ้อนเผื่ออนาคตที่อาจไม่มีวันมาถึง?"* |
| **5. The FinOps & Lock-in Economist**<br>*(นักเศรษฐศาสตร์คลาวด์)* | ต้นทุนรวมในการเป็นเจ้าของ (TCO), ค่าใช้จ่ายแฝง (Data Egress / Licensing), ต้นทุนเวลาทีมงาน และการป้องกันการผูกขาด (Vendor Lock-in) | *"ต้นทุนรวมทั้งค่า Cloud และเวลาวิศวกรดูแลในอีก 2 ปีข้างหน้าคือเท่าไหร่ และถ้าผู้ให้บริการขึ้นราคา 3 เท่า เราใช้เวลากี่วันในการย้ายออก?"* |

### Preset B: Quantitative Finance & Trading Preset
*(ใช้เมื่อประเมินกลยุทธ์เทรด, โมเดล Quant, Risk Management, Portfolio Allocation หรือ Algorithm)*

| ชื่อบทบาท | จุดยืนที่ต้องปกป้อง (Core Stance) | คำถามไม้ตายที่ใช้โจมตีข้อเสนอ (Kill-Shot Question) |
| :--- | :--- | :--- |

The Alpha Researcher**<br>*(นักวิจัยอัลฟาและกลยุทธ์)* | ความได้เปรียบเชิงสถิติ (Statistical Edge), ค่าคาดหวังเชิงบวก (Positive Expectancy), ความเร็วในการจับสัญญาณ และการหาความไร้ประสิทธิภาพของตลาด | *"ความได้เปรียบ (Edge) ของกลยุทธ์นี้เกิดจากพฤติกรรมตลาดหรือโครงสร้างข้อไหน และทำไมกองทุนรายใหญ่ถึงยังไม่ดูดกำไรส่วนนี้ไปจนหมด?"* |

| **3. The Overfitting & Data Skeptic**<br>*(ผู้ตรวจสอบความเอนเอียง)* | ความทนทานต่อข้อมูลนอกกลุ่มตัวอย่าง (Out-of-Sample Robustness), การจับผิด Data Snooping, Look-Ahead Bias, Survivorship Bias และ Regime Shift | *"ถ้าเราขยับพารามิเตอร์หลักไป ±15% หรือตัดช่วงตลาดที่ทำกำไรดีที่สุดออก 10% กำไรใน Backtest ยังเหลืออยู่ไหม หรือเป็นแค่การจูนตัวเลขให้เข้ากับอดีต?"* |
| **4. The Microstructure & Execution Realist**<br>*(ผู้เชี่ยวชาญการส่งคำสั่งจริง)* | ต้นทุนการซื้อขายจริง (Slippage, Spread, Market Impact, Funding Rate, Fee), ความหน่วงในการส่งคำสั่ง (Latency) และสภาพคล่องใน Order Book | *"เมื่อหักค่าธรรมเนียม, Funding Rate และ Slippage ในช่วงที่ตลาดผันผวนหนักแล้ว กำไรสุทธิต่อเทรด (Net Edge) ยังเป็นบวกอยู่จริงหรือไม่?"* |

## 2. Anti-Echo Chamber Rules
* **ห้ามประนีประนอมในบทบาทตัวเอง:** ที่ปรึกษาแต่ละคนต้องปกป้องจุดยืนของตนอย่างสุดตัวและใช้คำถามไม้ตายโจมตีจุดอ่อนของข้อเสนอโดยตรง
* **ระบุตัวเลขและกลไกจริง:** ห้ามพูดกว้างๆ ให้ระบุชื่อตัวแปร สมการ คอขวด หรือกลไกทางเทคนิคที่เกี่ยวข้องกับโจทย์นั้น

## 3. Deadlock Resolution Protocol (กลไกผ่าทางตัน 3 ขั้นตอน)
เมื่อคณะที่ปรึกษาเสียงแตกแบบ 50/50 ให้สังเคราะห์คำตัดสินสุดท้ายโดยใช้ลำดับตรรกะดังนี้:

### ขั้นตอนที่ 1: Reversibility & Ruin Filter (กรองความเสียหายถาวร)
* จำแนกว่าเป็นการตัดสินใจแบบ **Type 1 (ประตูบานเดียว - ย้อนกลับไม่ได้/พังแล้วจบ)** หรือ **Type 2 (ประตูสองทาง - แก้ไขทีหลังได้)**
* **กฎเหล็ก:** หากความเสี่ยงนำไปสู่ **ความเสียหายถาวร (Irreversible Ruin)** เช่น พอร์ตแตก, ระบบหลักพัง, หมุดโครงสร้างหลักผิดพลาด $\to$ **ให้สิทธิ์ยับยั้ง (Veto Power) แก่ฝ่ายความเสี่ยงทันที**
* หากความผิดพลาดสามารถย้อนกลับหรือแก้ไขได้โดยมีเพดานความเสียหายจำกัด $\to$ **เอนน้ำหนักไปทางฝ่ายลงมือทำ/โอกาส (Operator/Visionary)**

### ขั้นตอนที่ 2: Empirical Evidence Hierarchy (ชั่งน้ำหนักหลักฐาน 4 ระดับ)
| ลำดับชั้น | ประเภทหลักฐาน (Evidence Tier) | ตัวอย่างในทางปฏิบัติ | กฎการชั่งน้ำหนัก |
| :--- | :--- | :--- | :--- |
| **Tier 1 (สูงสุด)** | **กฎทางคณิตศาสตร์ ฟิสิกส์ และข้อจำกัดตายตัว** | สมการ Error Propagation, Kelly Criterion, สเปกฮาร์ดแวร์สูงสุด, งบประมาณ/เวลาจริง | **ชนะทุกความเห็น** (ความฝันเอาชนะกฎคณิตศาสตร์ไม่ได้) |
| **Tier 2** | **ข้อมูลเชิงประจักษ์จากระบบจริง / หน้างานจริง** | ผล Benchmark Production, Out-of-Sample Test, ข้อมูลสำรวจพื้นที่จริง | **ชนะทฤษฎีทั่วไป** และชนะการคาดเดา |
| **Tier 3** | **มาตรฐานอุตสาหกรรมและกรณีศึกษาเทียบเคียง** | Best Practices, เอกสารวิจัย, กรณีศึกษาระบบขนาดใกล้เคียงกัน | ใช้ตัดสินเมื่อยังไม่มีข้อมูล Tier 2 ของตัวเอง |
| **Tier 4 (ต่ำสุด)** | **สมมติฐานหรือความเชื่อที่ยังไม่มีตัวเลขรองรับ** | "คิดว่าลูกค้าน่าจะชอบ", "ตลาดน่าจะกลับตัว", "โค้ดน่าจะไม่พัง" | **ถูกปัดตกทันที** เมื่อปะทะกับ Tier 1–3 |

### ขั้นตอนที่ 3: Minimum Viable Falsification (การทดลองผ่าทางตัน)
หากข้อมูลทั้งสองฝั่งยังอยู่ในระดับ Tier 3–4 พอๆ กัน ให้ผ่าทางตันด้วยการสั่ง **"การทดลองจำกัดขอบเขตที่ประหยัดที่สุดเพื่อพิสูจน์ว่าสมมติฐานไหนผิด (Time-Boxed Validation Gate)"** พร้อมระบุตัวชี้วัดตัดจบ (Kill-Switch Metric)

## 4. Post-Decision Planning & Checkpointing Protocol

1. **Transition to Planning (`/plan`):** สรุปแนวทางการดำเนินงานเป็นแผนปฏิบัติการ

3. **Continuous Alignment:** สามารถเรียก `ask_question` เพิ่มเติมได้เสมอเมื่อพบจุดทางแยกย่อยในขั้นตอนการปฏิบัติ
